# Profiler capture analysis — [Ten] Test Player

Capture: ProfilerCaptures/Multiplayer-Project-Maew_2026-10-14_00-06-04.data (Unity 6000.3.4f1; 2,000 frames). I loaded the saved data file in Unity Profiler and exported the per-frame data and hierarchy; the source capture remains untouched.

The saved capture shows a sharp, sustained slowdown beginning around frame 1,200. Frames 0–1,199 have a 14.23 ms median (70.3 FPS) and 21.59 ms p95. Frames 1,200–1,999 have a 79.12 ms median (12.6 FPS), 103.11 ms p90, and 96.4% of frames exceed 33.3 ms. The worst frame is a 5.80 second scene-load stall; even after it settles, frames 1,400–1,999 remain at an 81.13 ms median (12.3 FPS). The user screenshot selects frame 2,056 of a 2,523-frame session. The saved data file contains 2,000 frames, but its frame 1,532 is exactly 101.932 ms, matching the screenshot’s selected CPU frame duration and key marker timings. Different frame numbering can reflect a saved subset and rebased indices; it does not establish a separate run.

At that 101.93 ms frame, the main-thread hierarchy attributes 39.25 ms to the Play Mode camera rendering path, including 37.73 ms in URP’s render loop and 24.47 ms in ScriptableRenderContext.Submit; it separately spends 31.17 ms in EditorLoop and 9.58 ms in another EditorLoop sample. A further 18.77 ms is a game PlayerLoop, including about 10.03 ms waiting at Semaphore.WaitForSignal. The render thread shows a 31.05 ms RenderLoop sample and URP render-graph work including 11.86 ms under DrawOpaqueObjects. The frame’s script update is only about 0.55 ms; named gameplay callbacks such as CoreMovement.Update() and AutomatedNetworkTransform.Update() are small in this selected frame. Physics work is also secondary here. The screenshot’s category summary similarly reports Rendering 31.48 ms, Scripts 8.60 ms, Physics 2.92 ms, and Others 58.54 ms.

This points to a combined Editor overhead plus rendering-path bottleneck. All four EditorLoop occurrences total approximately 42.18 ms of main-thread elapsed time in this sample (31.167 + 9.575 + 0.925 + 0.512 ms). Elapsed time can include waits; it is not a measurement of continuously active CPU execution. The scene’s rendering path costs another large block on both the main and render threads. The earlier overview screenshot shows roughly 11.55k batches and 5.99M triangles; that supports a high render workload, though those counts alone do not identify the specific mesh, material, shadow, or camera responsible. The saved capture has no usable GPU timing, so it does not establish whether GPU execution also limits frame rate.

The capture also records a one-time scene-load/static-batching event: LoadSceneOperation peaks at 5,433.61 ms, StaticBatching.Combine at 2,425.02 ms, and CombineMeshes at 1,715.72 ms. This explains the extreme load hitch around the transition, but it does not explain the continuing 12 FPS median after frame 1,400. In the selected slow frame, Semaphore.WaitForSignal appears in the game loop; long AsyncRead and PreloadManager wait tracks show waiting, which is mostly idle time rather than CPU work.

The immediate diagnostic priority is to reproduce the slow phase in a standalone Player build with the same scene and camera, then compare it with Editor Play Mode. Profile the Game camera’s URP render graph and inspect scene-view/editor overhead separately. The saved evidence already rules out script execution and physics as the main causes of this 101.93 ms frame; it does not yet identify which render feature or scene asset is the dominant rendering sub-cost.

Unity documents that `EditorLoop` contributes to the CPU Profiler’s `Others` category in Play Mode, and recommends profiling the Editor target to inspect those Editor costs in more detail: [Play mode and Editor samples](https://docs.unity3d.com/6000.3/Documentation/Manual/profiler-play-edit-samples.html).
